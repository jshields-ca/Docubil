# Releasing Docubil

This is for maintainers cutting a new version. Contributors don't need
this — see [CONTRIBUTING.md](CONTRIBUTING.md) instead.

## How it works

1. Commits on `main` follow [Conventional Commits](https://www.conventionalcommits.org/)
   (`feat:`, `fix:`, `docs:`, `chore:`, `security:`, etc.) — already
   enforced by convention via `npx cz` for commit authoring.

   **This matters for PR titles too, not just individual commits.**
   This repo squash-merges PRs, and a squash merge's commit subject is
   the PR title — not the original per-commit messages, which get
   demoted to the squash commit's body. `standard-version` only
   categorizes commits whose *subject line* matches `type: description`;
   a PR merged as "Add dark mode" produces a commit that's invisible to
   the changelog generator, even if every commit inside that PR was
   perfectly conventional. Always give the PR itself a conventional
   title before merging (the PR template checklist calls this out).
2. When you're ready to cut a release, run:
   ```bash
   npm run release
   ```
   This runs [`standard-version`](https://github.com/absolute-version/commit-and-tag-version),
   which:
   - Bumps the version in `package.json` based on the commit types since
     the last tag (`fix:` → patch, `feat:` → minor, `BREAKING CHANGE:` →
     major).
   - Regenerates `CHANGELOG.md` with a new versioned section, categorized
     by commit type per `.versionrc.json` (Added / Fixed / Security /
     Documentation / Maintenance / Changed).
   - Creates a commit and a git tag (`vX.Y.Z`) for the new version.

   To preview what a release would look like without changing anything:
   ```bash
   npm run changelog
   ```

3. Push the release commit and tag:
   ```bash
   git push --follow-tags origin main
   ```

4. Pushing the tag triggers `.github/workflows/release.yml`, which:
   - Builds a multi-arch (amd64/arm64) Docker image and pushes it to
     GitHub Container Registry as both `ghcr.io/jshields-ca/docubil:X.Y.Z`
     and `ghcr.io/jshields-ca/docubil:latest`.
   - Creates a GitHub Release with a body generated by
     `scripts/build-release-notes.mjs`: the categorized CHANGELOG.md
     section for that version up top (short, readable), with the full
     commit history for the release tucked into a collapsed
     `<details>` section for anyone who wants the detail.

5. That's it — anyone can now run Docubil without cloning the repo:
   ```bash
   curl -O https://raw.githubusercontent.com/jshields-ca/Docubil/main/docker-compose.release.yml
   docker compose -f docker-compose.release.yml pull
   docker compose -f docker-compose.release.yml up -d
   ```

## The first release needs a manual step

`npm run release` generates its changelog section entirely from commit
messages since the last tag — it can't see anything written by hand.
This repo currently has an `## [Unreleased]` section in `CHANGELOG.md`
written by hand (covering the Docubil rebrand, relicense, and frontend
rebuild, none of which are individually visible to the auto-generator
since those PRs were squash-merged before PR titles were required to be
conventional). Running `npm run release` as-is **would silently delete
that section** and replace it with a near-empty one.

For the **first** tagged release, do this instead of the automated
`npm run release` flow:

1. Decide the version number (this is a product call — is this a 1.0.0
   given it's a full public relaunch, or 0.1.0 since the project is
   still young? Your call).
2. Rename `## [Unreleased]` in `CHANGELOG.md` to `## [X.Y.Z] - YYYY-MM-DD`.
3. Bump the version without creating a tag: `npm version X.Y.Z --no-git-tag-version`
   (updates `package.json`/`package-lock.json` only).
4. Commit: `git commit -am "chore(release): X.Y.Z"`.
5. Tag manually: `git tag vX.Y.Z`.
6. Push: `git push --follow-tags origin main`.

From that point on, once every PR carries a conventional title before
squash-merging (see the PR template checklist), `npm run release` works
as designed for every subsequent release.

## First-time setup

The first time this workflow runs, GHCR will create a new package
(`docubil`) under your GitHub account/org. By default it's linked to
this repository's visibility, but double check under
**your profile → Packages → docubil → Package settings** that its
visibility matches what you want (public, since this is an open-source
project, unless you have a reason to keep images private).

## Manual release notes preview

To see what the GitHub Release body would look like for a tag without
actually pushing it:

```bash
node scripts/build-release-notes.mjs v1.2.0
```

(Requires that `v1.2.0`'s section already exists in `CHANGELOG.md` and,
ideally, that the tag exists locally so the commit-range detection
works — otherwise it falls back to the full history.)

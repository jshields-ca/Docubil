# Spike: can Docubil run entirely in the browser?

_Run 2026-10-17. Script: [`browser-first-analyze.mjs`](browser-first-analyze.mjs). Decision: [D-007](../../DECISIONS.md#d-007)._

## Question

Can the analysis and remediation Docubil does today (Express + `pdf-parse` +
`pdf-lib`, with an optional Python layer using `pikepdf` and `pdfplumber`) be
done with libraries that run in a browser? If so, files never leave the user's
device, the public site becomes a static site, and "install it locally without
admin rights" becomes "install the web app" (a PWA).

## Method

A Node script using only browser-capable libraries, `pdfjs-dist` 6.4 (Mozilla's
pdf.js) and `@cantoo/pdf-lib` 2.11, reimplements every check in
`src/python/analyze_pdf.py` and every fix in `src/python/remediate_pdf.py`. Then
it re-analyses its own output. It ran against seven PDFs: one generated by our
own test helper and six from pdf.js's public test corpus. The six cover tagged,
untagged, form-heavy (a prefilled IRS Form 1040), bookmarked, and figure-with-alt-text
documents. The results were compared with the Python layer's output on the same
files. Node runs the same pdf.js and pdf-lib code a browser does. The Node
results don't measure browser memory or speed: see "Still unproven" below.

## Results

| Check (Python layer today) | Browser-capable equivalent | Parity |
|---|---|---|
| Tagged: `/MarkInfo` + `/StructTreeRoot` | pdf-lib catalog lookups | ✅ same |
| Document language `/Lang` | pdf-lib catalog lookup | ✅ same |
| Bookmarks `/Outlines` | `pdfDocument.getOutline()` | ✅ same |
| Images per page (XObject scan) | operator list, `paintImageXObject` | ✅ same |
| Image alt text (assumed missing) | `page.getStructTree()`, `Figure` alt | ✅ **better**: real alt text read |
| Form fields + `/TU` tooltips | `getFieldObjects()` + widget `alternativeText` | ✅ **better**: nested fields found |
| Font sizes, heading candidates | `page.getTextContent()` transforms | ✅ same |
| Text contrast (vs white) | operator list fill colours | ✅ same approach |
| Fix: set `/Lang` | pdf-lib catalog write | ✅ |
| Fix: `/ViewerPreferences/DisplayDocTitle` | pdf-lib catalog write | ✅ |
| Fix: `/MarkInfo/Marked` | pdf-lib catalog write | ✅ |
| Fix: form field `/TU` | pdf-lib `getForm().getFields()` | ✅ (all 236 fields on the 1040) |

Remediated files reopen cleanly in pikepdf with their structure tree intact.
Analysis took 0.13–0.65 s per document. pdf.js's worker and main bundles add
about 1.8 MB of JavaScript (minified, before compression), loaded once and
cached.

### What the browser version would do better

The comparison found real accuracy problems in today's Python layer. They
matter whichever architecture wins:

1. **Nested form fields are invisible.** `analyze_pdf.py` reads only the
   top level of `/AcroForm/Fields`. On the IRS 1040 it reports **1 field**
   (`topmostSubform[0]`); the form has **236**. pdf.js flattens the hierarchy.
2. **Every image is reported as missing alt text**, even in a tagged PDF that
   has it, because the XObject scan never reads the structure tree.
   `getStructTree()` returns each `Figure`'s alt text directly.
3. **The structure tree is never examined**, so a tagged document full of
   generic `Div`/`P`/`NonStruct` elements scores the same as a properly
   structured one. pdf.js exposes every role, which makes checks like
   "headings exist and are nested in order" possible.

### Remediation problems found along the way (both architectures)

4. **`/MarkInfo/Marked = true` is set on documents with no structure tree.**
   That tells assistive technology the document is tagged when it isn't.
   Only set it when `/StructTreeRoot` exists. Untagged documents need real
   tagging, which is a "needs a human" item.
5. **Language is hard-coded to `en`** (`RemediationService._buildPythonFixes`),
   so a French document gets declared English and screen readers mispronounce
   all of it. The language should be detected from the text, or asked for.
6. **Generated tooltips aren't useful.** `"Please enter: topmostSubform[0]"`
   reads a machine name aloud. Tooltips should come from the field's visible
   label (text next to the widget), and anything we can't derive should be
   flagged for review instead of filled with filler.

## Still unproven (next steps before committing to the rewrite)

- **Browser memory on large files** (100+ pages, scanned image-heavy PDFs):
  run the same script in Chromium via Playwright against a 50 MB file.
- **pdf-lib save fidelity** on signed PDFs (rewriting invalidates
  signatures; we should warn rather than silently break them) and on
  encrypted PDFs.
- **`pdf-lib` itself is unmaintained** (last release 1.17.1, May 2022), and
  the server already depends on it. `@cantoo/pdf-lib` is an actively
  maintained fork with the same API, and the spike used it. It is the
  recommended replacement in either architecture.
- **Contrast against non-white backgrounds** still needs rendering
  (pdf.js can render to canvas, so this is possible in a browser in a way
  it isn't in today's Python layer).

## Conclusion

**Feasible.** Everything the Python layer does today can be done in the
browser with two well-supported libraries, and in three places it would be
more accurate. Phase 7 in [PLAN.md](../../PLAN.md) proceeds on this basis.
The "still unproven" items are its first milestone.
